Executive Summary

This document presents the results of a security review conducted by Nethermind Security for Vishwa smart contracts. Vishwa implements
a specialized extension layer built upon a fork of Morpho Blue. This extension introduces a tiered liquidation framework that enables both
restricted and public access controls. Specifically, the system provides two distinct mechanisms for managing undercollateralized positions:
a one-step liquidation path (accessible to the public or whitelisted users) and a two-step liquidation process exclusive to whitelisted
liquidators.
The audit comprises 510 lines of the Solidity code. The audit was performed using (a) manual analysis of the codebase, and (b) automated analysis tools. Along this document, we report 12 points of attention, where one is classified as Critical, two are classified as
High, one is classified as Medium and five are classified as Low, three are classified as Informational and Best Practices. The issues are
summarized in Fig. 1.
Security Findings Exceed Expected Levels
Based on the size of the codebase (510 lines of code) and our historical audit metrics, we would typically expect an average of one
issue per 150 lines of code, corresponding to approximately 3 to 4 issues for a project of this scope. However, the audit identified
12 issues, equivalent to approximately one issue every 42 lines of code, which is significantly above our baseline expectations.
Furthermore, our historical data shows that roughly 10% of reported issues fall into the high or critical severity categories. For
a codebase of this size, this would normally translate to zero or one high/critical issues. Instead, this audit uncovered three
high/critical severity issues, exceeding expected levels of risk.
These findings indicate that the overall security posture of the codebase is below what would normally be anticipated for a project
of this size and complexity and warrants particular attention from the development team.
Security Failures and Inadequate Testing
During the engagement, it was noted that the provided documentation lacked comprehensive details regarding the precise intended behavior and integration mechanics of the new extension. While these architectural intentions were later clarified during
sync calls with the developers, the initial ambiguity impacted the assumptions the Nethermind Security team used to evaluate the
codebase. Additionally, the provided test suite is currently non-functional.
The security review uncovered severe architectural flaws, most notably a Critical vulnerability that allows the extension’s core
safeguards to be bypassed entirely via direct interactions with the Morpho singleton. Furthermore, the Nethermind Security team
identified multiple systemic issues in which the extension’s internal calculations diverge from Morpho’s dynamic formulas, leading
to blocked liquidations and potential bad-debt accumulation.
Given the number of high-severity issues relative to the codebase size, the nature of these integration mismatches and the
absence of a functional test environment, it is strongly advised to repair and expand the test suite to ensure comprehensive code
coverage. Once the highlighted issues are resolved and the protocol is thoroughly tested, it is highly recommended that the
project undergo a subsequent security review prior to any mainnet deployment.

This document is organized as follows. Section 2 presents the files in the scope. Section 3 presents the summary of issues. Section 5
discusses the risk rating methodology. Section 6 details the issues. Section 7 discusses the documentation provided by the client for this
audit. Section 8 presents the test suite evaluation and automated tools used. Section 9 concludes the document.

System Overview

The Vishwa protocol introduced a Tiered Liquidation system that extends Morpho’s native liquidation logic with configurable access
controls, incentive structures, and commitment mechanisms.

4.1

Architecture & Core Components

The system employs a layered architecture in which extension contracts act as intermediaries between liquidators and the Morpho Blue
singleton. It consists of three main contracts:

4.1.1

TieredLiquidationMorpho

The central entry point for the tiered system. It wraps Morpho Blue’s liquidation function and enforces market-specific configurations,
including:
− Cooldowns: Minimum time required between successive liquidations of the same borrower.
− Liquidation Limits: Constraints on the maximum fraction of a position (maxLiquidationRatio) and minimum collateral seized
(minSeizedAssets).
− Protocol Fees & Bonuses: Vishwa calculates incentives independently of Morpho Blue’s native formula. The protocol collects a
fee from the liquidator’s bonus:
Bonus
a. Total Bonus = Seized1Assets×Liquidation
+Liquidation Bonus

b. Protocol Fee = Total Bonus × Fee Percentage

4

4.1.2

WhitelistRegistry

A per-market access control registry. It manages "Market Admins" who can whitelist specific addresses as authorized liquidators. It tracks
liquidation counts and determines whether a market is in Public or Whitelist-only mode.
It provides the canLiquidate(marketId, liquidator) function which determines authorization:
− If whitelist mode is disabled for a market, all addresses are authorized (returns true).
− If whitelist mode is enabled, only the market admin, the registry owner, or explicitly whitelisted addresses may liquidate.
Markets must be initialized by the owner. Once initialized, the market admin manages the liquidator set. The registry enforces that at least
one liquidator remains when whitelist mode is active.

4.1.3

HealthFactorLib

A utility library used to calculate the health factor ((collateral × price × LLTV)/borrowed) and determine the precise seizable and repayable
limits based on the tiered configuration.

4.2

Liquidation Flows

The protocol provides two distinct operational flows for liquidating unhealthy positions.

4.2.1

One-Step Liquidation (liquidate)

This method allows any user (or a whitelisted liquidator) to immediately liquidate an unhealthy position, provided the market is configured for
public liquidations. The liquidator repays a portion of the borrower’s debt and, in return, receives a corresponding amount of the borrower’s
collateral at a discount. This process is governed by market-specific parameters such as cooldown periods between liquidations and
maximum liquidation ratios.

4.2.2

Two-Step Liquidation

A commitment-based flow exclusive to whitelisted liquidators, designed to prevent front-running and provide execution certainty.
− Step 1: Request (requestLiquidation): The liquidator posts an ETH deposit to "lock" a borrower’s position. For the lockDuration,
no other liquidator (including one-step users) can target this position.
− Step 2: Execute (executeLiquidation): The original requester completes the liquidation within the lock window. The ETH deposit
is refunded upon success.
− Cancellation: If the lock expires without execution, the request can be cancelled by anyone to release the position, and the deposit
is returned to the requester.
Failed ETH refunds are tracked in failedRefunds and can be claimed later via claimFailedRefund().

Risk Rating Methodology

The risk rating methodology used by Nethermind Security follows the principles established by the OWASP Foundation. The severity of
each finding is determined by two factors: Likelihood and Impact.
Likelihood measures how likely the finding is to be uncovered and exploited by an attacker. This factor will be one of the following values:
a) High: The issue is trivial to exploit and has no specific conditions that need to be met;
b) Medium: The issue is moderately complex and may have some conditions that need to be met;
c) Low: The issue is very complex and requires very specific conditions to be met.
When defining the likelihood of a finding, other factors are also considered. These can include but are not limited to motive, opportunity,
exploit accessibility, ease of discovery, and ease of exploit.
Impact is a measure of the damage that may be caused if an attacker exploits the finding. This factor will be one of the following values:
a) High: The issue can cause significant damage, such as loss of funds or the protocol entering an unrecoverable state;
b) Medium: The issue can cause moderate damage, such as impacts that only affect a small group of users or only a particular part
of the protocol;
c) Low: The issue can cause little to no damage, such as bugs that are easily recoverable or cause unexpected interactions that
cause minor inconveniences.
When defining the impact of a finding, other factors are also considered. These can include but are not limited to Data/state integrity, loss
of availability, financial loss, and reputation damage. After defining the likelihood and impact of an issue, the severity can be determined
according to the table below.

6.4

[Medium] Reentrancy in _enforceNoActiveLock allows cooldown bypass and excess liquidation

File(s): src/extensions/TieredLiquidationMorpho.sol
Description: The _enforceNoActiveLock function uses an unsafe push pattern to refund ETH deposits to the previous liquidator. When
an expired request is found, it deletes the request and then sends ETH via _safeTransferETH, which performs a raw low-level. This hands
execution control to the recipient, who can re-enter any function in the contract.
1
2
3
4
5
6
7
8
9

function _enforceNoActiveLock(...) internal {
LiquidationRequest storage request = liquidationRequests[marketId][borrower];
if (request.status == LiquidationStatus.Pending) {
// ...
delete liquidationRequests[marketId][borrower];
// @audit low-level call to the request initiator
if (deposit > 0) _safeTransferETH(orig, deposit);
emit LiquidationRequestCancelled(marketId, borrower, msg.sender, true);
}
This function is called at the beginning of both liquidate and requestLiquidation. A whitelisted liquidator operating through a smart
contract can exploit this to bypass the cooldown and the maxLiquidationRatio cap. Consider the following scenario:
1. The attacker calls requestLiquidation for a target borrower and let the request expire;
2. Another liquidator ( or the attacker) calls liquidate for the same borrower. Inside _enforceNoActiveLock, the expired request is
deleted, and the attacker’s deposit is refunded via the ETH callback;
3. In their receive() function, the attacker re-enters requestLiquidation for the same borrower, recycling the just-refunded ETH as
the new deposit. A new LiquidationRequest is stored with the attacker as the liquidator;
4. The outer liquidate resumes: validates the position (still unhealthy, no cooldown), executes the Morpho liquidation seizing up to
maxLiquidationRatio of collateral, and sets lastLiquidationTime[marketId][borrower] = block.timestamp;
5. The attacker calls executeLiquidation using the request created in step 3. If the position remains unhealthy, a second Morpho
liquidation executes.
The result is that the borrower suffers two successive liquidations within a single cooldown window. If maxLiquidationRatio is 50%, the
attacker seizes 50% in the first liquidation and then up to 50% of the remaining position in the second, achieving a total collateral seizure
that is higher than the protocol intended cap at 50% per cooldown period.
Recommendation(s): Consider replacing the push-based ETH refund in _enforceNoActiveLock with a pull-only pattern. Alternatively,
consider adding a reentrancy guard to all external state-changing functions in the contract.

6.5

[Low] Pending liquidations can be executed in disabled markets

File(s): src/extensions/TieredLiquidationMorpho.sol
Description: The protocol allows admins to disable specific markets by setting the enabled flag to false. This is intended to act as a kill
switch or emergency stop for market activities.
When a market is disabled, the one-step liquidation process correctly reverts, and new two-step liquidation requests are blocked within the
requestLiquidation function.
However, the executeLiquidation function does not verify the config.enabled status. This enables liquidators who submitted a requestLiquidation
while the market was active to still call executeLiquidation to finalize the process after the market has been disabled by the owner.
This creates an inconsistency in the protocol’s emergency controls. If an owner disables a market, the expectation is that all liquidation
activities through the extension should halt immediately. Allowing pending two-step liquidations to execute against a disabled market
undermines the owner’s ability to use the enabled flag as an emergency stop.
Recommendation(s): Consider adding a check in the executeLiquidation function to check that the market is still enabled before
proceeding with the liquidation.

Documentation Evaluation

Software documentation refers to the written or visual information that describes the functionality, architecture, design, and implementation
of software. It provides a comprehensive overview of the software system and helps users, developers, and stakeholders understand how
the software works, how to use it, and how to maintain it. Software documentation can take different forms, such as user manuals, system
manuals, technical specifications, requirements documents, design documents, and code comments. Software documentation is critical
in software development, enabling effective communication between developers, testers, users, and other stakeholders. It helps to ensure
that everyone involved in the development process has a shared understanding of the software system and its functionality. Moreover,
software documentation can improve software maintenance by providing a clear and complete understanding of the software system,
making it easier for developers to maintain, modify, and update the software over time. Smart contracts can use various types of software
documentation. Some of the most common types include:
− Technical whitepaper: A technical whitepaper is a comprehensive document describing the smart contract’s design and technical
details. It includes information about the purpose of the contract, its architecture, its components, and how they interact with each
other;
− User manual: A user manual is a document that provides information about how to use the smart contract. It includes step-by-step
instructions on how to perform various tasks and explains the different features and functionalities of the contract;
− Code documentation: Code documentation is a document that provides details about the code of the smart contract. It includes
information about the functions, variables, and classes used in the code, as well as explanations of how they work;
− API documentation: API documentation is a document that provides information about the API (Application Programming Interface)
of the smart contract. It includes details about the methods, parameters, and responses that can be used to interact with the
contract;
− Testing documentation: Testing documentation is a document that provides information about how the smart contract was tested.
It includes details about the test cases that were used, the results of the tests, and any issues that were identified during testing;
− Audit documentation: Audit documentation includes reports, notes, and other materials related to the security audit of the smart
contract. This type of documentation is critical in ensuring that the smart contract is secure and free from vulnerabilities.
These types of documentation are essential for smart contract development and maintenance. They help ensure that the contract is
properly designed, implemented, and tested, and they provide a reference for developers who need to modify or maintain the contract in
the future.
